In production, all of the portal's state lives in the composition's internal PostgreSQL. Backups of this database are the only recovery path: the installation starts with an empty database and there is no data migration from the SQLite of earlier versions. This page covers the logical backup, the restore, and what else needs to be stored alongside it.

## What the database holds

The `postgres` service (image `postgres:17-alpine`, database `wcui`, user `wcui`) persists its data in the named volume `wcui_pg_data`. The volume survives `docker compose down`; only `docker compose down -v` deletes it.

The database contains the portal's data:

- users, with their password hashes, and groups;
- login sessions;
- the image catalog, with limits and access grants;
- the instance records and usage metrics;
- each user's SSH identity, with the private key encrypted;
- the registered MCP servers, with environment variables and headers encrypted;
- the AGENTS.md document library and the agent skills.

The design of the persistence layer is in [Database](/architecture/database/).

### What is not in the database

- **The data of each user desktop.** Each user/image pair has its own named Docker volume, outside PostgreSQL. `pg_dump` does not cover them.
- **The covers uploaded by the administrator.** They live in `/data/uploads/images`, in the portal's `wcui_db` volume.
- **The TLS certificates.** They live in the `caddy_data` volume and are reissued by Caddy if the volume is lost.
- **The environment secrets.** `deploy/.env` is not part of any volume.

## Why the backup is sensitive

:::caution
Treat the backup file as a secret. It contains every user's email, the password hashes, the login sessions, the encrypted SSH private keys and the encrypted secrets of the MCP servers.
:::

The SSH private keys and the MCP server secrets are encrypted at rest with `WCUI_SSH_KEY_ENCRYPTION_KEY` (Fernet). This has two operational consequences:

- Anyone who obtains the backup **and** this key can decrypt every user's SSH private key and the MCP server secrets. Store the two in separate places.
- A backup restored **without** the same `WCUI_SSH_KEY_ENCRYPTION_KEY` leaves the SSH identities and the MCP server secrets unreadable. Store the key (and the rest of `deploy/.env`) with the same care as the backup, off the host.

Store backups encrypted and with restricted access, and do not leave them in the host's `deploy/` directory longer than necessary.

## Logical backup

Run from the `deploy/` directory, with the composition up:

```bash
docker compose exec -T postgres pg_dump -U wcui wcui > wcui-$(date +%F).sql
```

`pg_dump` produces a consistent snapshot without needing to stop the portal. Because PostgreSQL publishes no port on the host, the command runs inside the database container.

Take a backup before any update that changes the schema, and keep a periodic routine that matches how much data you are willing to lose.

## Restore

The restore is done with the portal stopped, so that nothing writes to the database during the load:

```bash
docker compose stop portal
docker compose exec -T postgres psql -U wcui wcui < wcui-2026-11-06.sql
docker compose start portal
```

Replace `wcui-2026-11-06.sql` with the file you want to restore.

:::note
The command above loads the backup on top of the existing database. The file generated by `pg_dump` without additional options recreates tables and data, but does not remove objects that already exist; a clean restore assumes an empty `wcui` database, like that of a fresh installation before the portal's first startup.
:::

After restoring, the portal reconciles instance state during its own startup. Check the result with the [Post-deploy checklist](/operations/post-deploy-checklist/).

## Development and earlier versions (SQLite)

In development and in the tests the database is a single SQLite file (`WCUI_DB_PATH`, by default `/data/webcontainerui.db`), without `WCUI_DATABASE_URL`. The same applies to deploys of versions that predate the adoption of PostgreSQL, whose file remains intact in the `wcui_db` volume. Copying and restoring this file are described in [Rollback](/operations/rollback/).

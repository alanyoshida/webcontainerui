Isolation between users does not depend on a single check. A request to `/i/{uuid}/` only reaches the container after passing through four independent layers, and the secrets the portal stores are encrypted at rest. This page describes each layer, what it guarantees and — with the same emphasis — what it does not guarantee.

None of these layers limits what the portal itself can do on the host. That is a separate subject, covered in [Trust surface](/security/trust-surface/).

## Overview

| Layer | Where it is applied | What it blocks |
|---|---|---|
| 1. Authenticated session | Portal, on every non-public route | Anonymous request |
| 2. Owner check | Session proxy and data plane authorization | Authenticated user accessing someone else's instance |
| 3. Random per-instance credential | Inside the container | Whoever reaches the container without going through the portal |
| 4. Topological isolation | Internal Docker network, no published port | Access to the container from outside the host |

Layers 1 and 2 are the portal's decision. Layer 3 is enforced by the container itself. Layer 4 is a property of the network topology, not of code.

## Layer 1 — authenticated session

Every route that is not explicitly public requires a valid session cookie: the API, the admin panel and the instance path. Without a session, the response is "not authenticated" and does not reveal whether the resource exists.

The session is a random 256-bit token, stored in the database only as a hash, with expiration (12 hours by default) and immediate revocation on logout. Disabling an account revokes its existing sessions. The details of cookie, limiter and password hash are in [Login hardening](/security/login-hardening/).

**Guarantees:** that every action is attributed to a known, active user.

**Does not guarantee:** that whoever presents the cookie is the right person. There is no second factor. A stolen cookie is valid until it expires or is revoked. In addition, content served from inside the user's container runs on the same origin as the portal and can use the user's session — this is an accepted risk, described in [Audits](/security/audits/).

Specification: [auth](https://github.com/alanyoshida/webcontainerui/blob/main/openspec/specs/auth/spec.md).

## Layer 2 — owner check

Having a valid session is not enough to reach an instance: the portal checks that the authenticated user is its owner. The check happens on every HTTP request and also when opening the persistent channel (WebSocket) that carries the interactive session.

- A nonexistent instance and an instance belonging to another owner produce the same response (`404`), so it is not possible to enumerate other people's identifiers.
- An instance of the owner that is not running responds `409`, without attempting to reach the container.
- When the administrator revokes the grant of an image to a group, the affected instances are stopped immediately and access to them is refused from then on.
- Creating an instance requires a current permission on the image; a user's permission is the union of the permissions of the groups they belong to.

**Guarantees:** that an authenticated user does not enter another user's instance through the portal, even knowing the identifier.

**Does not guarantee:** anything about who reaches the container without going through the portal — that is what layers 3 and 4 exist for. And it does not protect against an administrator: administrators control users, groups, the catalog, and the documents and MCP servers the portal propagates to the instances.

Specifications: [session-proxy](https://github.com/alanyoshida/webcontainerui/blob/main/openspec/specs/session-proxy/spec.md) and [access-control](https://github.com/alanyoshida/webcontainerui/blob/main/openspec/specs/access-control/spec.md).

## Layer 3 — random per-instance credential

Each instance is born with its own username/password pair, generated by the portal with `secrets.token_urlsafe` (8 bytes for the username, 16 bytes for the password) and handed to the container at creation. The service inside the container — the webtop interface or the agent's terminal — requires this credential on every request.

- The portal (or, in production, the data plane) injects the credential into the forwarded request. The user never types it and never receives it.
- Any `Authorization` header sent by the client is discarded before forwarding and replaced with the instance's credential.
- The credential does not appear in error responses or in reflected headers.

**Guarantees:** that reaching the container's port is not sufficient to enter the session. In the penetration test, an "attacker" container on the same network received `401` when trying the "victim" container.

**Does not guarantee:** protection for any other service listening inside the container. The credential protects only the interface process that requires it. A development server, a debugging API or anything the user or an agent image brings up on another port is reachable by the other users' containers (see layer 4). It also does not protect against whoever reads the portal's database, where the credential is stored in cleartext.

## Layer 4 — topological isolation

Instance containers **never publish a port on the host**. They exist only on the internal Docker network (`wcui_net` in production), and the only path from outside to inside is the edge (Caddy) — which only forwards what the portal approved. The portal does not publish a port in production either; only Caddy exposes 80 and 443.

**Guarantees:** that no user container is reachable from the internet or from the host's network directly, and that distinct Docker networks are isolated from each other.

**Does not guarantee isolation between users inside the internal network.** This is the most important limit on this page:

:::caution[All instances share the same network]
The portal creates all instance containers on the same Docker network. There is no per-user or per-instance network. From inside their own container, a user (who has root there) can scan ports and reach the containers of all other users, the portal on port 8000, Caddy and PostgreSQL. What stops them is layer 3 on other people's containers, layer 1 on the portal, and the database password. This point was recorded in the penetration test as finding B4 and remains open — see [Audits](/security/audits/).
:::

Practical consequence for whoever maintains images: **every listener inside an instance container must require the internal credential or listen only on `localhost`**. This is not yet a formal contract of the agent images; it is a recommendation. See [Agent images](/architecture/agent-images/).

Topological isolation also does not restrict outbound traffic: a container reaches what the host reaches, including the internet and, depending on your environment, other machines on the host's network.

## Session data plane

In production Caddy carries `/i/{uuid}/` directly to the instance containers; the portal stops relaying the frames and only decides authorization. The full design is in [Session data plane](/architecture/session-data-plane/). From a security standpoint, this changes the surface in three ways:

- **Caddy reaches the instance containers.** It already lived on `wcui_net`; now `reverse_proxy` uses that access. The containers still have no port published on the host — isolation from the outside remains topological.
- **Shared secret.** `forward_auth` presents `WCUI_DATA_PLANE_SECRET` to the internal authorization endpoint (`/internal/data-plane/authorize`). Without the correct secret, the endpoint responds `401` and nothing is forwarded — it fails closed, including when the portal is down. The comparison is constant-time, and an empty secret disables the endpoint instead of opening it. The endpoint is not exposed by the edge: Caddy responds `404` to `/internal/*` coming from outside, and it does not appear in the public API schema.
- **Routes are configuration, not code.** The portal writes one snippet per instance to the `caddy_routes` volume, with validated id and container name (only `[A-Za-z0-9_.-]`); the reload command is fixed in the portal, never derived from user input.

The portal remains the only component that decides authorization; Caddy only carries what the portal approved. With the data plane active, layers 1 and 2 are evaluated at the internal endpoint on every request and on every channel opening, and the layer 3 credential travels from the portal to Caddy in the authorization response and from Caddy to the container — never to the client.

What this does **not** change:

- The internal endpoint is reachable from inside the internal network, and therefore also by the instance containers. What prevents a container from querying it is the secret. Whoever obtains `WCUI_DATA_PLANE_SECRET` and is on the internal network would still need a valid session cookie of the owner to receive an instance's credential — the secret alone authorizes nothing.
- The session proxy inside the portal remains registered. In production it is shadowed by the edge routing; it is the development and test path and a defense in depth, with the same checks.

Specification: [stream-data-plane](https://github.com/alanyoshida/webcontainerui/blob/main/openspec/specs/stream-data-plane/spec.md).

## SSH identity encrypted at rest

Each user has their own SSH key pair, generated by the portal, so that `git` and `ssh` work inside the instances without manual configuration.

- The private key is stored encrypted with Fernet, using `WCUI_SSH_KEY_ENCRYPTION_KEY`. The portal refuses to start without a valid Fernet key — there is no "without encryption" mode.
- The portal **only generates** keys. It never receives or stores a pre-existing private key; import is refused.
- The API returns only the public key. Viewing and regenerating the identity is restricted to the owner.
- Regenerating replaces the identity in all of the user's live instances, running or stopped.

**Guarantees:** that a database leak, on its own, does not hand over private keys.

**Does not guarantee:**

- Protection against whoever has the database **and** the Fernet key. The two together are equivalent to all the private keys.
- Protection inside the container. The private key is injected in cleartext into `/config/.ssh/` (mode `600`) so that `git` can use it. Any process running in the instance — including an AI agent and the packages it installs — can read it. Treat the public key registered on GitHub, GitLab or Bitbucket as a credential that that person's agents can use.
- Automatic rotation. The change happens when the user triggers regeneration; the old public key has to be removed manually from the remote services.

Specification: [ssh-identity](https://github.com/alanyoshida/webcontainerui/blob/main/openspec/specs/ssh-identity/spec.md).

## Encrypted MCP secrets

The MCP servers registered by the administrator can carry environment variables and headers with secrets (API tokens, for example). These values are encrypted in the database with the same Fernet infrastructure as the SSH identity, and the API returns only the key names, never the values.

**Guarantees:** that the values are not stored in cleartext in the database and do not come back through the admin API.

**Does not guarantee:** secrecy with respect to the users of the linked images. For the agent to use the MCP server, the configuration — with the values — is written inside the instance's container. An MCP secret linked to an image must be considered known to every user who has access to that image. Use minimum-scope credentials, intended to be shared with that group.

:::note
The SSH identity and the MCP secrets use the same key (`WCUI_SSH_KEY_ENCRYPTION_KEY`). Losing the key makes both unrecoverable; leaking it together with the database exposes both. See [Environment variables](/operations/environment-variables/) and [Backup and restore](/operations/backup-and-restore/).
:::

## Summary of what no layer covers

- The portal's authority over the host ([Trust surface](/security/trust-surface/)).
- Network reachability between containers of different users (finding B4, open).
- The fact that the container's content runs on the portal's origin (finding M3, accepted).
- A malicious or compromised administrator.
- Container escape through a flaw in the kernel or in the Docker runtime.

The status of each item raised in an audit is in [Audits](/security/audits/).
